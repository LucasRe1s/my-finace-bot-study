# Módulo de Pedidos Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** App Next.js independente em `pedidos/` para registrar pedidos de mercados e enviá-los à granja por um bot do Telegram com botões de status.

**Architecture:** Regras de negócio em `src/lib/` como funções puras ou que recebem dependências (`Repo`, `TelegramClient`) por parâmetro, testáveis com fakes em memória. Páginas e Server Actions do Next só fazem auth + chamam esses serviços com as implementações reais (Supabase service role, Bot API via fetch). O webhook do Telegram é um Route Handler.

**Tech Stack:** Next.js 16.2.9 (App Router, `proxy.ts`), React 19.2.4, TypeScript, Tailwind 4, `@supabase/ssr` 0.12 + `@supabase/supabase-js` 2.x, Vitest.

**Spec:** `docs/superpowers/specs/2026-10-14-pedidos-design.md`

## Global Constraints

- Nenhuma dependência de código fora de `pedidos/` (módulo será movido para outro repo).
- RLS habilitado em todas as tabelas, sem policies; dados só via servidor com `SUPABASE_SERVICE_ROLE_KEY`. A anon key só é usada para Supabase Auth.
- Status: `erro_envio | enviado | aceito | recusado | em_entrega | entregue | cancelado`.
- Webhook valida `X-Telegram-Bot-Api-Secret-Token` (401 se errado) e sempre responde 200 nos demais casos.
- Textos da UI e do bot em português; datas DD/MM HH:mm no fuso `America/Sao_Paulo`.
- Variáveis: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_WEBHOOK_SECRET`.

### Task 2: Regras de status

**Files:** `src/lib/status.ts`, `src/lib/__tests__/status.test.ts`

**Produces:** `nextStatus(current: OrderStatus, action: OrderAction, actor: Actor): { ok: true; to: OrderStatus } | { ok: false; reason: string }`, `STATUS_LABEL: Record<OrderStatus, string>`, `isFinal(s): boolean`.

Tabela: `reenviar` web erro_envio→enviado; `aceitar` granja enviado→aceito; `recusar` granja enviado→recusado; `sair_entrega` granja aceito→em_entrega; `entregar` web em_entrega→entregue; `cancelar` web {enviado, aceito, em_entrega, erro_envio}→cancelado.

- [ ] Testes: cada transição válida; ator errado (`aceitar` por web) → `ok:false`; status final → reason `"Pedido já <label>"`; `cancelar` em `entregue` → falha. Ver falhar, implementar, ver passar. Commit.

### Task 4: Serviços de pedido

**Files:** `src/lib/repo.ts`, `src/lib/telegram.ts` (interface + `createTelegramClient(token)`), `src/lib/orders.ts`, `src/lib/__tests__/fakes.ts`, `src/lib/__tests__/orders.test.ts`

**Interfaces:**
```ts
interface Repo {
  getSettings(): Promise<Settings>;
  saveSettings(patch: Partial<Settings>): Promise<void>;
  listProducts(opts?: { includeInactive?: boolean }): Promise<Product[]>;
  saveProduct(p: { id?: string; name: string; description: string; units_per_box: number }): Promise<void>;
  setProductActive(id: string, active: boolean): Promise<void>;
  createOrder(input: NewOrderInput): Promise<string>;           // via RPC create_order
  getOrder(id: string): Promise<Order | null>;
  listOrders(status?: OrderStatus): Promise<Order[]>;
  listEvents(orderId: string): Promise<OrderEvent[]>;
  transitionOrder(id: string, from: OrderStatus, to: OrderStatus, actorLabel: string): Promise<boolean>; // update condicional + evento; false se status mudou
  setTelegramMessageId(id: string, messageId: number): Promise<void>;
}
interface TelegramClient {
  sendMessage(chatId: number, text: string, keyboard: InlineKeyboard | null): Promise<number>;
  editMessage(chatId: number, messageId: number, text: string, keyboard: InlineKeyboard | null): Promise<void>;
  answerCallback(callbackQueryId: string, text?: string): Promise<void>;
}
type NewOrderInput = { customer_name: string; notes: string; created_by: string; items: { product_id: string; boxes: number }[] };
```
**Produces:** `createOrder(deps, input): Promise<{ id: string; sent: boolean; error?: string }>`, `dispatchOrder(deps, orderId): Promise<{ sent: boolean; error?: string }>`, `applyOrderAction(deps, { orderId, action, actor, actorLabel }): Promise<{ ok: boolean; message: string }>`, onde `deps = { repo: Repo; tg: TelegramClient }`.

- [ ] Testes com FakeRepo/FakeTelegram: criar pedido envia mensagem e guarda message_id; sem granja vinculada → `erro_envio` + evento + `error` "Granja não vinculada"; Telegram lança erro → `erro_envio`; validação: cliente vazio, sem itens, boxes ≤ 0 → erro sem gravar; `applyOrderAction` cancelar edita mensagem; transição inválida → `ok:false` sem editar; `transitionOrder` retornando false → `ok:false` "Pedido foi atualizado por outra pessoa"; falha ao editar mensagem não desfaz status; `reenviar` em `erro_envio` envia e vira `enviado`, se falhar continua `erro_envio`. Implementar. Commit.
